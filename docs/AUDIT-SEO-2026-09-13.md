## 3. P0 — ce qui coûte du trafic aujourd'hui

### P0-1. La SERP de marque est occupée par un ancien site français, pas par le site canonique

Preuves :

- requête `"maxlananas" Minecraft builder portfolio` → résultat n°1 : `https://maxlananas-builds.pages.dev/` avec un contenu **français** riche : « Je conçois des mondes extraordinaires », builds nommés et décrits (Fort Napoléon / Guadeloupe, Larressingle / Gers / Occitanie, Immeuble avec pont, Parisien haussmannien, Organique Fleurs, Maison en bois, Spawn Fight4Glory), section « Builder Minecraft depuis 2020 », compétences (WorldPainter, FAWE/WorldEdit, Axiom, Arceon/EzEdits), email de contact et formulaire ;
- `maxlananas.is-a.dev` **n'apparaît pas** dans ces résultats, ni sur une requête par phrase exacte du site actuel ;
- cette même URL sert aujourd'hui le portfolio anglais : `https://maxlananas-builds.pages.dev/robots.txt` et `/sitemap.xml` sont ceux de ce dépôt (sitemaps pointant vers `maxlananas.is-a.dev`) ;
- Wayback CDX sur `maxlananas-builds.pages.dev` : **aucun snapshot** (`[]`) → l'ancien contenu français n'est archivé nulle part.

Conséquences : deux propriétés pour une même personne, signaux de marque divisés, contenu français indexé puis remplacé par de l'anglais générique (perte probable du trafic non-marque FR : « builder minecraft », noms de lieux, « spawn événement »), et risque de confusion d'entité pour les systèmes de recherche.

À faire :

1. **Récupérer l'ancien contenu français** avant qu'il ne disparaisse des caches : déploiements précédents du projet Cloudflare Pages (`maxlananas-builds`), dépôt local, ou export des `_data`. C'est la seule source connue de descriptions de builds en français.
2. Décider d'**un seul hôte canonique**. Si le projet Cloudflare Pages ne sert qu'aux previews, vérifier que l'en-tête est bien appliqué : `curl -sI https://maxlananas-builds.pages.dev/ | grep -i x-robots-tag` doit renvoyer `noindex` (règle `_headers` `https://:project.pages.dev/*`). Sinon, supprimer le déploiement de production du projet CF ou le rediriger en 301 vers `maxlananas.is-a.dev`.
3. Dans GSC + Bing : inspection d'URL, demande de suppression/mise à jour pour l'ancienne URL française, puis soumission des sitemaps.

## 4. P1 — technique, performance, médias

### P1-1. Le LCP de l'accueil dépend entièrement du JavaScript
`templates/home.html:78` produit `<div class="masonry" id="masonry" aria-busy="true"></div>` : **aucune image dans le HTML servi**, ni en mode source ni en mode optimisé. Les tuiles sont créées par `script.js:buildGrid()` puis chargées par IntersectionObserver + `LoadQueue`. Il n'y a aucun `<link rel="preload" as="image">`. Le plus grand élément visible de l'accueil est donc une image découverte après exécution du JS : c'est le principal risque Core Web Vitals (LCP mobile), et la galerie de l'accueil reste invisible pour un moteur qui n'exécute pas le JS (le catalogue `/builds/` compense pour l'indexation, pas pour le LCP).
Correctif : pré-rendre 6 à 8 tuiles dans le HTML en mode optimisé (le manifeste fournit déjà largeur/hauteur réelles et variantes AVIF/WebP), `fetchpriority="high"` sur la première, `preload` de cette première image, et laisser le JS remplacer/compléter la grille.

### P1-2. 240 Mo déployés et 67 minutes de build pour 101 photos
Artefact `github-pages` du déploiement : **239 608 586 octets** ; run `Portfolio — deploy — main` n° 34177126902 : `01:34:53 → 02:42:25` soit **67 minutes**. Cause : `IMAGE_WIDTHS = [320, 640, 960, 1600, 2560]` × AVIF (q70, effort 6) + WebP (q90, effort 6) pour 101 originaux (`tools/prepare-images.mjs:RECIPE`). Or la grille est plafonnée à `GRID_MAX_WIDTH = 960` (`image-utils.js`) : 1600 et 2560 ne servent qu'à la lightbox.
Correctifs : supprimer 2560 (ou le générer à la demande), garder 1600 uniquement pour les images réellement ouvertes, baisser `effort` AVIF à 4 en CI, mettre en cache les variantes (déjà prévu) ; à terme, héberger la galerie sur un CDN d'images (Cloudflare R2/Images) plutôt que dans l'artefact Pages. Effet attendu : déploiement divisé par 3 à 5, build très raccourci.
Nettoyage associé : 38 artefacts Actions, dont plusieurs `validated-site` de 239 Mo **non expirés** (~700 Mo de stockage) → supprimer les anciens.

### P1-3. Les originaux dépendent d'une release GitHub tierce
`gallery-data.js:RELEASE_BASE` = `https://github.com/MaxLananas/Asset-Portfolio/releases/download/images-v1/` : les 101 originaux, tous les liens « open original » et le repli de `page.js`/`image-loader.js` pointent vers un autre dépôt. Risques : suppression/renommage de la release = 101 liens morts ; téléchargements lents (302 vers `release-assets.githubusercontent.com`) ; en mode source, les 101 images passent par le proxy tiers `wsrv.nl` (104 références dans le HTML commité et **104 `image:loc` sur wsrv.nl dans `sitemap-images.xml`**), ce qui sort les images du domaine et donc de Google Images.
Correctif : conserver les originaux dans le dépôt d'assets ou sur R2, et ne garder `wsrv.nl` qu'en repli d'urgence ; régénérer `sitemap-images.xml` du snapshot commité pour qu'il ne déclare pas des URLs que la page publiée n'utilise pas.

### P1-4. GitHub Pages ne permet ni cache ni en-têtes : `_headers` est inerte en production
Le site canonique est publié par GitHub Pages (`build_type: "workflow"`, `cname: maxlananas.is-a.dev`, `custom_404: true`, certificat approuvé jusqu'au 2026-11-13). `_headers`/`_redirects` ne s'y appliquent pas (le dépôt le documente déjà). Conséquences réelles : pas de `Cache-Control: immutable` sur des assets pourtant hashés (`styles-YAQO6EE4.css`, `app-RQB2P7UR.js`), pas d'en-têtes de sécurité, pas de `X-Robots-Tag` pilotable, compression non maîtrisée.
Correctif : placer Cloudflare devant le domaine (ou publier le canonique sur Cloudflare Pages avec domaine personnalisé) — `_headers` devient alors réellement utile, et les redirections hôte/http→https/www deviennent possibles.

### P1-5. Domaine gratuit `is-a.dev`
Sous-domaine enregistré via le registre is-a.dev (le compte a même un fork `register`), aucune autorité de domaine propre, pas d'apex ni de `www`, dépendance à un tiers pour la résolution. Pour un site dont l'objectif est d'être trouvé sur « minecraft builder », c'est un plafond.
Correctif : nom de domaine propre (`maxlananas.fr`, `.build`, `.dev`), 301 depuis `maxlananas.is-a.dev`, mise à jour de `SITE.url` (`content/site.js:3`) puis `npm run seo:render` pour régénérer canonicals, sitemaps, JSON-LD et `_headers`.

### P1-6. La vidéo n'est pas éligible aux résultats vidéo
`projects/iprof-redesign/index.html` déclare un `MediaObject` (name, description, contentUrl, thumbnailUrl, encodingFormat, `duration: PT47.68S`, `inLanguage: fr`) — pas un `VideoObject` — et il n'existe **aucun sitemap vidéo**. `MediaObject` n'ouvre aucun résultat enrichi.
Correctif : passer en `VideoObject` avec une `uploadDate` réelle (date de dépôt du fichier, connue du build — pas une date inventée), conserver `duration`/`thumbnailUrl`/`contentUrl`, ajouter `publisher`/`creator`, et lister la vidéo dans `sitemap.xml` (ou un `sitemap-video.xml`). Le lecteur est déjà bien optimisé : `preload="none"`, poster 1200×630 de 42 Ko, facade cliquable, MP4 servi en byte-range (testé par `tools/verify-live.mjs`).

### P1-7. Une seule image sociale pour 27 pages sur 35
`og:image` = `/assets/social/portfolio.png` (1200×630, 41 Ko) sur **27 pages**, y compris les 7 pages de galerie qui contiennent 16 vraies images chacune et les hubs `projects/`, `development/`, `buildtheearth/`. Seules 8 pages ont une carte dédiée (iProf + 6 mods Modrinth).
Correctif : générer au build une carte par page (collage des 2–4 images de la page ou couverture du projet + titre) avec `sharp`, déjà en dépendance ; renseigner `og:image` par page dans `content/pages.js`. Impact : CTR des partages Discord/Reddit/X et présentation dans Discover.

### P1-8. 94 images sur 242 avec `alt=""`
Une partie est légitime (logo de marque 28×28 dans l'en-tête des 33 pages document, vignette de carte à côté d'un titre déjà textuel). Mais parmi elles : les **couvertures Modrinth** de `projects/index.html` (11) et `development/index.html` (11), les **logos de crédits** BTE/Endorah/Fight4Glory/MrBeast sur `buildtheearth/index.html` (3), les visuels de plusieurs fiches projet (`bedrock-height-guard`, `bidvault`, `deathpoint`, `maxos`, `pineappleui`, `sentinel`, `bte-*` : 2 à 4 chacun). `tools/project-content.mjs:22-23` impose `alt: ""` pour `cover` et `icon`.
Correctif : `alt` court et descriptif (« Colorflow — sélecteur de couleurs dans Minecraft, couverture Modrinth »), `alt=""` réservé aux décorations réelles. Effet : éligibilité Google Images sur les requêtes par nom de mod.

### P1-9. Titles et descriptions hors gabarit SERP
- **10 titles > 60 caractères** (jusqu'à 72 : `development/`), dont `buildtheearth/` 61, `guides/…` 65, `bedrock-height-guard` 65, `nostalgia-ultra` 65, `builders-utilities-bt-corsica` 63, `colorflow` 63, `pineappleui` 62, `tracebte` 61, `bte-france-guidelines` 61 ;
- **14 descriptions > 160 caractères** (jusqu'à 195 : `nostalgia-ultra`), dont `bedrock-height-guard` 181, `jukeboxplus` 180, `deathpoint` 174, `now-playing-irl` 174, `sculk-vision` 171, `sentinel` 167, `colorflow` 165, `buildtheearth` 164.
Correctif : 50–60 / 140–155 caractères, requête cible en début de title (ex. « Minecraft builder — builds 1:1, spawns & tools | MaxLananas »), ajouter une garde de longueur dans `tools/seo-check.mjs` pour empêcher la régression.

### P1-10. Aucune fraîcheur : toutes les dates sont au 7 septembre 2026
`content/page-dates.json` : `published`/`modified`/`reviewed` = `2026-09-07` pour les 34 URLs ; `sitemap.xml` : 34 `lastmod` identiques ; `2026-09-07` apparaît 104 fois dans le HTML et « 7 September 2026 » 20 fois. Un `lastmod` uniforme et figé est un signal faible, et rien n'a bougé depuis la mise en ligne.
Correctif : ne pas dater artificiellement (le dépôt a raison de refuser ça), mais **publier** : notes de release à chaque version Modrinth, un guide par mois, une étude de build. Mettre à jour `page-dates.json` uniquement quand le contenu change vraiment.

### P1-11. Ni Bing, ni IndexNow, ni mesure
`content/site.js:7` → `verification: { google: "l9cbo…", bing: "" }`. Aucun fichier de clé IndexNow, aucun analytics (ni GA4, ni Plausible/Umami). Le pilotage repose donc sur un seul outil, sans données de comportement ni CWV terrain.
Correctif : vérifier Bing Webmaster (variable `BING_SITE_VERIFICATION` déjà supportée par le workflow), publier une clé IndexNow, installer une mesure légère respectueuse du RGPD, puis suivre LCP/INP/CLS p75 dans GSC dès qu'il y a du trafic.

### P1-12. Favicon lourd et `favicon.ico` absent
`assets/icons/favicon-96.png` : 96×96 en **17,4 Ko** PNG, déclaré en `<link rel="icon">` sur les 36 documents **et** chargé comme `<img width="28" height="28">` dans l'en-tête des 33 pages document. Aucun `favicon.ico` → requête `/favicon.ico` en 404 systématique (bruit dans les logs et certains outils).
Correctif : icône WebP/AVIF 2–3 Ko ou SVG (le logo est déjà un SVG inline dans `templates/home.html`), ajouter un `favicon.ico` 32×32, et réutiliser le SVG plutôt qu'un raster dans l'en-tête.

## 5. P2 — hygiène, cohérence et opportunités

1. **Mode source incohérent avec le mode publié.** Dans les snapshots commités (et donc dans toute preview sans build) : `.photo-media { aspect-ratio: 4/3 }` + `object-fit: contain` (`style.css:390-391`) et `width="640" height="480"` imposés par `tools/seo-content.mjs:17` quelle que soit la proportion réelle → images letterboxées et dimensions intrinsèques fausses (CLS). Le build optimisé, lui, utilise les vraies dimensions. À corriger pour que le repli reste fidèle.
2. **Pagination faible.** 7 pages × 16 images avec un texte quasi identique ; passer à 24–32 images/page (4 URLs au lieu de 7) + 2–3 phrases propres à chaque page (période, thème, crédit dominant) réduirait le nombre d'URLs à faible valeur et augmenterait la densité utile.
3. **`/search/` est à 87 % identique à l'accueil** (Jaccard 0,874). Il est `noindex` et sans canonical : c'est correct, à conserver tel quel.
4. **Fichiers sources publiés à la racine** (visibles en mode legacy) : `image_v2-Photoroom.png` 223 Ko, `cropped-500x500Endorah_-_Copie-2322200814.png` 86 Ko, `1701523229mr-beast-logo-…png` 22 Ko, `Logo_BTE_France-…png` 20 Ko, `FFFlauta-200.otf` 17 Ko. Ils ne servent qu'à `tools/prepare-static.mjs`. À déplacer dans un dossier non publié (ex. `sources/`, exclu de la publication) pour éviter du bruit crawlable et du poids inutile.
5. **Opportunité MrBeast non exploitée.** 6 captures sont créditées « 10-builder collaboration featured in a video by MrBeast » avec lien YouTube (`gallery-data.js:CREDITS.mrbeast`). C'est le plus gros potentiel d'autorité du site : page dédiée « Featured in », outreach pour un lien en description de la vidéo, publication sur X/Reddit avec le portfolio en lien.
6. **Preuve communautaire existante.** r/BuildTheEarth cite « Napoléon Fort, Guadeloupe (built by MaxLananas) » : en faire une étude de build nommée exactement ainsi (P0-2) et la partager dans la communauté → lien entrant pertinent.
7. **Liens retour Modrinth/GitHub à poser.** Les fiches du site pointent vers Modrinth et GitHub ; l'inverse n'est pas vérifiable ici (page Modrinth rendue côté client). Ajouter l'URL de la fiche portfolio dans les champs « links » de chaque projet Modrinth et dans les README des dépôts concernés.
8. **Dépôt public `tezdsfsdsdfg`** : 27 Mo de fichiers `.schem`, nom illisible, poussé le 13/09. Bruit sur le profil GitHub. Soit le renommer/décrire correctement, soit en tirer une vraie page « Schematics & builds à télécharger » (contenu unique, téléchargeable, lien depuis les études de builds).
9. **CI : bon garde-fou à conserver.** La PR #5 (refonte GSAP de l'accueil) a échoué sur `npm run seo:check` (run 34373651774, étape « Run npm run seo:check ») : toute refonte visuelle qui vide le HTML statique est bloquée. Aucune PR ouverte au 13/09. À préserver absolument.
10. **Accessibilité (revue statique, sans navigateur).** Points positifs : skip-links, `aria-live` sur le compteur de résultats, `role="tablist"` avec `aria-selected`, champs de recherche labelisés, `aria-busy` sur la grille, SVG décoratifs en `aria-hidden`. À valider côté utilisateur avec Lighthouse/axe : contraste du thème sombre (`--text-dim` sur `#0a0a0b`), taille des cibles tactiles dans les contrôles de galerie, et focus dans la lightbox ; l'`<img class="lb-img">` sans `width`/`height` provoque un déplacement à l'ouverture de la lightbox.
11. **`Person.image` = `apple-touch-icon.png`** (un logo, pas une personne) dans le graphe JSON-LD de toutes les pages, et aucune photo d'auteur sur `/about/`. Pour un `ProfilePage`, une image de l'auteur (ou au minimum un avatar cohérent avec GitHub/Instagram/Modrinth) renforce l'entité.
12. **Contact incomplet.** Le seul canal est un lien Discord ; l'ancien site français exposait un email et un formulaire. Un email professionnel (ou un formulaire via service tiers sans JS bloquant) améliorerait la conversion et la cohérence NAP/entité — à ajouter dans `content/site.js` et le graphe `Person.contactPoint`.
